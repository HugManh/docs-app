Chương 7. Request Convention

Purpose

Request Convention chuẩn hóa cách Client gửi dữ liệu đến Server, bao gồm:

  • Path Parameters
  • Query Parameters
  • Request Body
  • Headers
  • Content Negotiation
  • Idempotency
  • Metadata

Mục tiêu là đảm bảo mọi API trong hệ thống có cách gửi request thống nhất, giúp Client dễ sử dụng và Backend dễ bảo trì.

Rules

  • Request MUST sử dụng đúng vị trí của dữ liệu.
  • Path Parameter MUST dùng để định danh Resource.
  • Query Parameter MUST dùng để truy vấn.
  • Request Body MUST chứa dữ liệu cần tạo hoặc cập nhật.
  • Header MUST chứa metadata.
  • Request MUST sử dụng JSON nếu không có quy định khác.
  • Request SHOULD nhất quán giữa các endpoint.

Path Parameters

Purpose

Định danh Resource.

Ví dụ:

GET /users/15

PATCH /courses/5

Rules

Path Parameter:

  • MUST đại diện cho Identity.
  • MUST NOT dùng cho Filter.
  • SHOULD rõ nghĩa.

Đúng

GET /users/15

Sai

GET /users?id=15

trong trường hợp truy cập một Resource duy nhất.

Multiple Path Parameters

Ví dụ

GET /courses/5/lessons/10

Ý nghĩa:

Lesson 10 thuộc Course 5.

Không nên:

GET /courses/5/modules/2/lessons/10/questions/50

URI quá sâu.

Query Parameters

Purpose

Query Parameter chỉ dùng để truy vấn.

Bao gồm:

  • Filtering
  • Pagination
  • Searching
  • Sorting
  • Projection
  • Include

Ví dụ

GET /users?page=1&pageSize=20

GET /users?status=active

GET /courses?q=nestjs

GET /orders?sort=-createdAt

GET /users?fields=id,name

Rules

Query Parameter:

  • MUST không thay đổi dữ liệu.
  • SHOULD độc lập.
  • SHOULD có tên rõ ràng.

Naming Convention

Khuyến nghị dùng camelCase.

page

pageSize

createdAt

startDate

includeDeleted

Không nên:

page_size

PageSize

PAGE_SIZE

Boolean Parameters

Đúng

includeDeleted=true

published=false

Không nên

deleted=1

deleted=yes

deleted=ok

Enum Parameters

Ví dụ

status=draft

status=published

status=archived

Không nên

status=1

trừ khi Enum đã được chuẩn hóa.

Array Parameters

Khuyến nghị

GET /users?ids=1,2,3

hoặc

GET /users?ids[]=1&ids[]=2

Trong toàn bộ hệ thống chỉ nên chọn một quy ước.

Date Parameters

Khuyến nghị ISO 8601.

2026-07-29

hoặc

2026-07-29T08:30:00Z

Không nên

29/07/2026

hoặc

07-29-2026

Request Body

Purpose

Body chứa dữ liệu cần gửi lên Server.

Ví dụ

POST /users

Không nên

POST /users?name=John

PUT Body

PUT nên gửi đầy đủ Resource.

Ví dụ

PATCH Body

PATCH chỉ gửi field thay đổi.

Ví dụ

Empty Body

GET

GET /users

Không nên gửi Body.

DELETE

Thông thường cũng không nên gửi Body.

Nếu cần truyền nhiều ID để xóa, ưu tiên thiết kế endpoint Bulk riêng thay vì gắn Body vào DELETE.

Ví dụ:

POST /users/bulk-delete

hoặc

POST /users/batch

Correlation ID

Khuyến nghị

X-Correlation-Id

để trace request xuyên suốt nhiều service.

Nếu Client không truyền, API Gateway hoặc Backend có thể tự sinh.

Idempotency-Key

Áp dụng cho:

POST /payments

POST /orders

Ví dụ

Idempotency-Key:
8b1a9953-c461

Giúp tránh tạo trùng dữ liệu khi Client retry.

Common Mistakes

❌

POST /users?id=10

✔

POST /users

❌

GET /users

Body:

{
   "page":1
}

✔

GET /users?page=1

❌

GET /users?token=abc

✔

Authorization: Bearer ...

❌

PATCH

{
   "id":15,
   "name":"Alice"
}

✔

PATCH /users/15

{
   "name":"Alice"
}

Identity nên lấy từ Path thay vì lặp lại trong Body.

Best Practices

  • Identity nằm ở Path.
  • Truy vấn nằm ở Query.
  • Payload nằm ở Body.
  • Metadata nằm ở Header.
  • Sử dụng JSON mặc định.
  • Chuẩn hóa tên Query Parameter.
  • Dùng ISO 8601 cho ngày giờ.
  • Không truyền thông tin nhạy cảm qua Query String.
  • Sử dụng X-Correlation-Id để hỗ trợ tracing.
  • Áp dụng Idempotency-Key cho các POST có nguy cơ tạo trùng.

Checklist

  • Identity truyền qua Path Parameter.
  • Query Parameter chỉ dùng cho truy vấn.
  • Body chỉ chứa dữ liệu tạo hoặc cập nhật.
  • Header chỉ chứa metadata.
  • Authorization sử dụng Header.
  • JSON là định dạng mặc định.
  • Sử dụng ISO 8601 cho ngày giờ.
  • Không gửi Body với GET.
  • Không truyền dữ liệu nhạy cảm qua Query String.
  • Có hỗ trợ Correlation ID và Idempotency Key khi cần.
