Chương 5. HTTP Methods

Purpose

HTTP Method (hay HTTP Verb) xác định ý nghĩa của một request đối với Resource. Việc sử dụng đúng HTTP Method giúp API tuân thủ chuẩn HTTP, dễ dự đoán, tận dụng được các tính năng của proxy, CDN, cache và các công cụ trung gian.

Một trong những lỗi phổ biến nhất của REST API là sử dụng sai Method, ví dụ dùng POST cho mọi thao tác hoặc dùng GET để thay đổi dữ liệu.

Rules

  • GET MUST chỉ dùng để đọc dữ liệu.
  • POST MUST dùng để tạo Resource mới hoặc thực hiện Action không idempotent.
  • PUT MUST thay thế toàn bộ Resource.
  • PATCH MUST cập nhật một phần Resource.
  • DELETE MUST xóa Resource.
  • GET MUST NOT thay đổi trạng thái hệ thống.
  • GET, PUT và DELETE SHOULD giữ tính idempotent.
  • Method MUST phản ánh đúng ý nghĩa theo HTTP RFC 9110.

GET

Purpose

Lấy Representation của Resource.

Ví dụ:

GET /users

GET /users/10

GET /courses

Rules

GET:

  • MUST NOT tạo dữ liệu.
  • MUST NOT cập nhật dữ liệu.
  • MUST NOT xóa dữ liệu.
  • SHOULD hỗ trợ cache.
  • SHOULD hỗ trợ Conditional Request.

Correct Examples

GET /users

GET /courses?page=1

GET /orders?status=paid

GET /users/15

Incorrect Examples

Sai:

GET /users/10/delete

Sai:

GET /createOrder

Sai:

GET /users?update=true

Why

GET có thể được:

  • Browser preload
  • Browser prefetch
  • Search Engine crawl
  • CDN cache
  • Retry tự động

Nếu GET làm thay đổi dữ liệu sẽ gây hậu quả nghiêm trọng.

POST

Purpose

POST dùng để:

  • tạo Resource mới
  • gửi command
  • submit dữ liệu
  • thực hiện Action không idempotent

Create Resource

POST /users

Body

Response

201 Created
Location: /users/15

Business Action

Có những hành động không biểu diễn được bằng CRUD.

Ví dụ:

POST /orders/10/cancel

POST /orders/10/pay

POST /users/15/reset-password

Đây là trường hợp hợp lệ.

Không nên

POST /users/delete

POST /users/update

POST /users/get

PUT

Purpose

PUT thay thế toàn bộ Resource.

Ví dụ hiện tại

PUT

Sau PUT

Toàn bộ Representation được thay thế.

Rules

PUT:

  • SHOULD gửi đầy đủ Resource.
  • SHOULD idempotent.
  • SHOULD thay thế toàn bộ dữ liệu.

Không nên

PUT /users/10

Body

nếu API chỉ cập nhật một field.

Trường hợp này nên dùng PATCH.

PATCH

Purpose

PATCH cập nhật một phần Resource.

Ví dụ

Hiện tại

PATCH

Kết quả

Rules

PATCH:

  • chỉ gửi field thay đổi.
  • không yêu cầu gửi toàn bộ Resource.
  • có thể không idempotent tùy cách triển khai.

Ví dụ

PATCH /users/10

PUT vs PATCH

PUTPATCH
Thay thế toàn bộCập nhật một phần
Gửi toàn bộ dữ liệuGửi field thay đổi
IdempotentCó thể không
Thích hợp ReplaceThích hợp Update

Recommendation

Trong REST API hiện đại:

  • CRUD thông thường nên ưu tiên PATCH.
  • PUT chỉ dùng khi thực sự thay thế toàn bộ Representation.

DELETE

Purpose

Xóa Resource.

Ví dụ

DELETE /users/10

Rules

DELETE:

  • SHOULD idempotent.
  • SHOULD trả về 204 nếu xóa thành công và không có nội dung trả về.
  • MAY trả về 200 nếu có Response Body.
  • MAY trả về 202 nếu xử lý bất đồng bộ.

Ví dụ

DELETE /orders/20

Response

204 No Content

HEAD

HEAD giống GET nhưng không trả Body.

Ví dụ

HEAD /files/10

Dùng để:

  • kiểm tra tồn tại
  • lấy Content-Length
  • lấy Last-Modified
  • lấy ETag

OPTIONS

OPTIONS cho biết endpoint hỗ trợ Method nào.

Ví dụ

OPTIONS /users

Response

Allow:
GET
POST
OPTIONS

Thường được Browser dùng trong CORS Preflight.

CONNECT

Không dùng trong REST API.

TRACE

Không khuyến nghị bật.

Lý do:

  • ít giá trị
  • có nguy cơ bảo mật

Nên tắt trên Web Server.

Safe Methods

Safe Method không làm thay đổi dữ liệu.

Bao gồm:

  • GET
  • HEAD
  • OPTIONS

Có thể gọi nhiều lần mà không tạo tác dụng phụ.

Idempotent Methods

Một request được gọi nhiều lần nhưng trạng thái cuối cùng không đổi.

Ví dụ

DELETE /users/10

Gọi:

1 lần

hay

100 lần

đều dẫn đến:

User không còn tồn tại.

Common Mistakes

Sai 1

POST /getUsers

Đúng

GET /users

Sai 2

POST /updateUser

Đúng

PATCH /users/{id}

Sai 3

GET /users/delete/5

Đúng

DELETE /users/5

Sai 4

PUT /users/10

Body

Nếu chỉ cập nhật email thì nên dùng

PATCH /users/10

Action Endpoint

Một số Action không phải CRUD.

Ví dụ

POST /orders/10/pay

POST /orders/10/refund

POST /orders/10/cancel

POST /users/10/verify-email

POST /users/10/send-verification

Đây là ngoại lệ được chấp nhận.

Asynchronous Processing

Nếu xử lý lâu:

POST /imports

Response

202 Accepted

Body

Client theo dõi:

GET /jobs/abc123

Best Practices

  • Luôn chọn Method đúng với ngữ nghĩa HTTP.
  • Không dùng POST cho mọi thao tác.
  • Không dùng GET để thay đổi dữ liệu.
  • Ưu tiên PATCH cho cập nhật thông thường.
  • Chỉ dùng PUT khi thay thế toàn bộ Resource.
  • Action nghiệp vụ nên dùng POST /resource/{id}/action.
  • Tận dụng HEAD và OPTIONS khi phù hợp.

Prisma Example

Lưu ý: Prisma không phân biệt PUT và PATCH. Cả hai đều thường sử dụng update(). Sự khác biệt nằm ở quy ước của API và cách validate request body, không phải ở ORM.

Checklist

  • GET chỉ dùng để đọc dữ liệu.
  • POST dùng để tạo mới hoặc thực hiện Action.
  • PUT chỉ dùng để thay thế toàn bộ Resource.
  • PATCH dùng để cập nhật một phần Resource.
  • DELETE chỉ dùng để xóa Resource.
  • Không dùng GET để thay đổi trạng thái hệ thống.
  • Không dùng POST thay cho CRUD thông thường.
  • Hiểu rõ sự khác biệt giữa Safe và Idempotent.
  • Action nghiệp vụ được thiết kế theo POST /resource/{id}/action.
