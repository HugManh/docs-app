Chương 3. URI Design

Purpose

URI (Uniform Resource Identifier) là điểm tiếp xúc đầu tiên giữa Client và API. Một URI được thiết kế tốt giúp API dễ đọc, dễ ghi nhớ, dễ dự đoán và duy trì tính nhất quán trên toàn hệ thống.

Mục tiêu của chương này là chuẩn hóa cách thiết kế URI để mọi endpoint trong hệ thống đều tuân theo cùng một quy ước.

Rules

  • URI MUST đại diện cho Resource.
  • URI MUST sử dụng danh từ (noun).
  • Resource Collection MUST sử dụng số nhiều (plural).
  • URI MUST sử dụng chữ thường (lowercase).
  • URI SHOULD sử dụng dấu gạch ngang (-) để phân tách từ.
  • URI MUST NOT chứa động từ.
  • URI SHOULD ổn định theo thời gian.
  • Path Parameter MUST dùng để định danh Resource.
  • Query Parameter MUST dùng để lọc, sắp xếp và phân trang.
  • URI MUST NOT phản ánh cấu trúc database hoặc implementation.

URI Anatomy

Ví dụ:

GET /api/v1/users/123/orders?status=paid&page=1&pageSize=20
Thành phầnGiá trị
Base Path/api
Version/v1
Collection/users
Resource ID123
Child Resource/orders
Querystatus=paid&page=1&pageSize=20

Resource Naming

Rule

URI phải biểu diễn Resource.

Đúng:

/users
/orders
/courses
/categories

Sai:

/getUsers
/createUser
/saveOrder
/updateCourse

Why

HTTP Method đã biểu diễn hành động.

Ví dụ:

GET /users
POST /users
PATCH /users/10
DELETE /users/10

Không cần lặp lại hành động trong URI.

Plural Nouns

Rule

Collection MUST sử dụng danh từ số nhiều.

Đúng:

/users
/orders
/courses

Sai:

/user
/order
/course

Why

Collection luôn đại diện cho nhiều resource.

Ngay cả khi:

GET /users/1

thì /users vẫn là collection.

Exception

Nếu Resource bản chất không đếm được:

/equipment
/news
/information

Có thể giữ nguyên.

Lowercase

Rule

URI MUST sử dụng chữ thường.

Đúng:

/users
/course-categories

Sai:

/Users
/UserList
/CourseCategories

Why

Một số Web Server phân biệt hoa/thường.

/Users
/users

có thể là hai endpoint khác nhau.

Word Separator

Rule

Nên sử dụng dấu -.

Đúng:

/course-categories
/user-profiles

Không khuyến nghị:

/course_categories
/courseCategories

Why

Dễ đọc hơn.

Đặc biệt với URI dài.

No Verb

Không đưa động từ vào URI.

Sai:

/create-user
/get-users
/update-course
/delete-order

Đúng:

POST /users
GET /users
PATCH /courses/{id}
DELETE /orders/{id}

Stable URI

URI không nên thay đổi theo UI.

Sai:

/mobile/users
/web/users
/admin/users

Nên:

/users

Authorization quyết định quyền truy cập, không phải URI.

Path Parameters

Rule

Path Parameter dùng để định danh Resource.

Đúng:

GET /users/10

GET /courses/5

Sai:

GET /users?id=10

khi đang truy cập một resource cụ thể.

Query Parameters

Rule

Query Parameter dùng cho:

  • filtering
  • pagination
  • sorting
  • searching
  • field selection

Ví dụ:

GET /users?page=1&pageSize=20

GET /courses?status=published

GET /orders?sort=createdAt

GET /users?q=john

Nested Resource

Rule

Nested Resource dùng để biểu diễn quan hệ sở hữu (ownership).

Ví dụ:

GET /users/10/orders

nghĩa là:

Orders thuộc User 10.

Không nên lồng quá sâu.

Đúng:

/users/10/orders

Không khuyến nghị:

/users/10/orders/8/items/20/comments/5

Why

URI dài gây khó đọc và khó bảo trì.

Resource vs Relationship

Ví dụ:

/users/10/orders

Nếu Order tồn tại độc lập:

/orders/99

nên ưu tiên truy cập trực tiếp.

Nested Resource không nên thay thế endpoint gốc.

Action Endpoint

Có một số hành động không phải CRUD.

Ví dụ:

POST /orders/10/cancel
POST /orders/10/pay
POST /users/10/reset-password

Đây là ngoại lệ được chấp nhận khi:

  • hành động mang tính nghiệp vụ
  • không thể biểu diễn bằng CRUD

File Resource

Đúng:

/files
/files/{id}

Không nên:

/uploadFile
/downloadFile

Upload và Download sẽ được phân tích ở chương riêng.

Current User

Không nên:

/users/123/profile

nếu Client chỉ được thao tác trên chính mình.

Nên:

GET /me
PATCH /me
GET /me/orders

Search Endpoint

Nếu tìm kiếm đơn giản:

GET /users?q=john

Nếu tìm kiếm phức tạp:

POST /users/search

để truyền body lớn.

Không nên:

POST /searchUser

Batch Endpoint

Có thể sử dụng:

POST /users/batch

POST /users/bulk

Sẽ được chuẩn hóa ở chương Bulk Operations.

Versioning

Nếu version nằm trên URI:

/v1/users

Không nên:

/users/v1

hoặc:

/version1/users

URI Length

Không có giới hạn trong HTTP RFC.

Tuy nhiên nên:

  • dưới 2 KB
  • tránh query quá dài
  • tránh nested quá nhiều tầng

Examples

Đúng:

GET /users

GET /users/10

GET /users/10/orders

POST /orders

PATCH /orders/5

DELETE /orders/5

GET /course-categories

Sai:

GET /getUsers

POST /createUser

POST /deleteOrder

GET /User

GET /Users

GET /userOrders

GET /users?id=10

Counter Examples

❌

POST /updateCourseName

✔

PATCH /courses/{id}

❌

GET /DeleteUser

✔

DELETE /users/{id}

❌

POST /user/create

✔

POST /users

Best Practices

  • URI luôn biểu diễn Resource.
  • HTTP Method biểu diễn hành động.
  • Dùng danh từ số nhiều.
  • Dùng chữ thường.
  • Dùng dấu - để phân tách từ.
  • Không để implementation ảnh hưởng URI.
  • Không thiết kế URI theo màn hình giao diện.
  • Chỉ dùng Nested Resource khi biểu diễn quan hệ sở hữu.
  • Giữ URI ngắn, ổn định và dễ dự đoán.

Checklist

  • URI biểu diễn Resource.
  • Không có động từ trong URI.
  • Collection dùng danh từ số nhiều.
  • Chỉ sử dụng chữ thường.
  • Dùng - để phân tách từ.
  • Path Parameter chỉ dùng để định danh Resource.
  • Query Parameter chỉ dùng cho truy vấn.
  • Nested Resource không quá sâu.
  • URI không phụ thuộc UI hoặc Database.
  • Action Endpoint chỉ dùng cho nghiệp vụ đặc biệt.
