Chương 10. Filtering

Purpose

Filtering cho phép Client chỉ lấy những Resource thỏa mãn các điều kiện cụ thể thay vì tải toàn bộ dữ liệu.

Một cơ chế Filtering tốt giúp:

  • Giảm dữ liệu truyền tải.
  • Giảm xử lý phía Client.
  • Tăng hiệu năng hệ thống.
  • Hỗ trợ tìm kiếm theo nhiều tiêu chí.
  • Dễ mở rộng khi bổ sung điều kiện mới.

Filtering chỉ thay đổi tập dữ liệu trả về, không thay đổi Resource.

Rules

  • Filtering MUST sử dụng Query Parameters.
  • Filtering MUST không thay đổi dữ liệu.
  • Filter Parameter SHOULD có tên rõ ràng.
  • Các Filter MUST có thể kết hợp với nhau.
  • Filtering SHOULD hoạt động cùng Pagination và Sorting.
  • API MUST bỏ qua các Filter không được hỗ trợ hoặc trả lỗi rõ ràng theo quy ước của hệ thống.
  • Không sử dụng Path Parameter cho Filtering.

Filtering vs Searching

Filtering

GET /users?status=ACTIVE

↓

Chọn các User có trạng thái ACTIVE.

Searching

GET /users?q=john

↓

Tìm User chứa từ khóa “john”.

Filtering có điều kiện xác định.

Searching thường mang tính gần đúng (fuzzy).

Basic Filtering

Ví dụ

GET /courses?level=N5

Multiple Filters

Ví dụ

?status=ACTIVE

&role=ADMIN

Range Filtering

Ví dụ

GET /orders

?minAmount=100000

&maxAmount=500000

SQL

Ngày tháng

GET /orders

?from=2026-01-01

&to=2026-12-31

Khuyến nghị sử dụng:

  • from
  • to

hoặc

  • startDate
  • endDate

Chỉ chọn một quy ước trong toàn hệ thống.

Boolean Filtering

Đúng

GET /users?enabled=true

GET /courses?published=false

Không nên

enabled=1

enabled=yes

Enum Filtering

GET /orders

?status=PENDING

GET /orders

?status=COMPLETED

Giá trị Enum nên được chuẩn hóa và ghi rõ trong OpenAPI.

Filtering by IDs

Ví dụ

GET /users?ids=1,2,3

SQL

Hoặc

GET /users?ids[]=1&ids[]=2

Toàn bộ hệ thống chỉ nên sử dụng một cách biểu diễn.

Multiple Values

Ví dụ

GET /courses

?level=N4,N5

↓

Null Filtering

Ví dụ

GET /users?phone=null

Khuyến nghị rõ ràng hơn:

GET /users?hasPhone=false

Hoặc

GET /users?phoneExists=false

Tránh truyền literal "null" nếu có thể.

Date Filtering

Khuyến nghị ISO 8601.

GET /logs

?from=2026-07-01T00:00:00Z

&to=2026-07-31T23:59:59Z

Không nên

01/07/2026

Nested Filtering

Ví dụ

?teacherId=10

Không nên

teacher.id=10

trong Query Parameter nếu không có quy ước rõ ràng.

Relationship Filtering

Ví dụ

GET /orders

?customerId=100

↓

Lọc Order theo Customer.

Soft Delete

Ví dụ

GET /users?includeDeleted=true

Hoặc

GET /users?deleted=true

Khuyến nghị chọn một cách và áp dụng nhất quán.

Filter Operators

Có hai cách phổ biến.

Option 1

Tên Parameter rõ nghĩa.

minPrice

maxPrice

from

to

Khuyến nghị.

Option 2

Toán tử trong Query.

price[gte]=100000

price[lte]=500000

Hoặc

price.gt=100000

Phù hợp với các API có bộ lọc động phức tạp.

Recommendation

Đối với đa số Enterprise CRUD API:

Ưu tiên

minAmount

maxAmount

from

to

Dễ đọc hơn.

Default Filtering

Không nên mặc định trả cả dữ liệu đã xóa mềm.

Ví dụ

GET /users

↓

Chỉ trả dữ liệu còn hiệu lực.

Muốn lấy dữ liệu đã xóa:

GET /users?includeDeleted=true

Unknown Filter

Ví dụ

GET /users?abc=123

Có hai lựa chọn.

Option A

Bỏ qua.

Ưu điểm

  • Backward Compatible.

Nhược điểm

  • Client khó phát hiện lỗi.

Option B

400 Bad Request

Khuyến nghị cho Internal API và Enterprise API để phát hiện lỗi sớm.

Best Practices

  • Dùng Query Parameter cho Filtering.
  • Tên Filter rõ ràng và dễ hiểu.
  • Chuẩn hóa cách biểu diễn khoảng giá trị.
  • Hỗ trợ kết hợp nhiều Filter.
  • Luôn Filter trước rồi mới Sort và Pagination.
  • Thiết kế Index theo các Filter phổ biến.
  • Không lạm dụng LIKE '%keyword%' trên dữ liệu lớn.
  • Chỉ chọn một quy ước biểu diễn nhiều giá trị cho toàn hệ thống.

Checklist

  • Filtering sử dụng Query Parameter.
  • Không sử dụng Path cho Filtering.
  • Hỗ trợ nhiều Filter cùng lúc.
  • Khoảng giá trị dùng min/max hoặc from/to thống nhất.
  • Boolean dùng true/false.
  • Enum được chuẩn hóa.
  • Có Index cho Filter thường dùng.
  • Filter hoạt động cùng Sorting và Pagination.
  • Quy định rõ cách xử lý Filter không hợp lệ.

Ghi chú: Từ chương này trở đi, các chương Searching, Sorting, Field Selection và Include/Expand sẽ được thiết kế để kết hợp hoàn chỉnh với Filtering, tạo thành một chuẩn truy vấn thống nhất cho toàn bộ Collection API.
