Chương 2. REST Principles

Purpose

Chương này trình bày các nguyên lý cốt lõi của REST (Representational State Transfer) và cách áp dụng chúng vào thiết kế API hiện đại.

REST không phải là một giao thức hay một framework, mà là một kiến trúc (Architectural Style) được Roy Fielding mô tả trong luận án tiến sĩ năm 2000. Một REST API tốt không chỉ sử dụng HTTP đúng cách mà còn phải tuân theo các ràng buộc (Constraints) của REST để đạt được khả năng mở rộng, hiệu năng và tính độc lập giữa Client và Server.

Rules

  • API MUST được thiết kế theo Resource-Oriented Design.
  • Resource MUST được định danh bằng URI.
  • HTTP Method MUST biểu diễn hành động.
  • API SHOULD tận dụng đầy đủ ngữ nghĩa của HTTP.
  • Server MUST stateless.
  • Resource SHOULD có representation ổn định.
  • Response SHOULD có khả năng cache khi phù hợp.
  • Client MUST NOT phụ thuộc vào implementation của Server.
  • URI MUST đại diện cho resource, không phải hành động.
  • API SHOULD có hành vi nhất quán giữa các resource.

REST Constraints

REST định nghĩa 6 ràng buộc chính.

1. Client - Server

Purpose

Client chỉ quan tâm:

  • URI
  • Request
  • Response

Server chịu trách nhiệm:

  • Database
  • Business Logic
  • Authentication
  • Authorization
  • Validation

2. Stateless

Rule

Server MUST NOT lưu trạng thái của request trước đó.

Server phải nhớ session trong RAM.

Điều này làm giảm khả năng mở rộng.

Why

Stateless giúp:

  • Scale ngang dễ dàng.
  • Load Balancer hoạt động hiệu quả.
  • Không phụ thuộc vào một server cụ thể.
  • Khởi động lại server không làm mất session.

Pros

  • Dễ mở rộng.
  • Dễ triển khai.
  • Dễ cache.
  • Dễ failover.

Cons

  • Request lớn hơn do phải gửi đầy đủ thông tin.
  • JWT có thể làm tăng kích thước Header.

Resource-Oriented Design

REST xoay quanh Resource.

Ví dụ:

User
Course
Order
Invoice
Lesson
Comment

Không xoay quanh hành động.

Đúng:

GET /users
POST /users
PATCH /users/10
DELETE /users/10

Sai:

POST /createUser
POST /deleteUser
POST /updateUser

URI biểu diễn Resource

URI là danh từ.

Đúng:

/users
/orders
/courses

Sai:

/getUsers
/saveCourse
/updateOrder

Hành động thuộc về HTTP Method.

HTTP Method biểu diễn Action

Ví dụ:

MethodÝ nghĩa
GETĐọc
POSTTạo
PUTThay thế
PATCHCập nhật một phần
DELETEXóa

Không nên tạo:

POST /deleteUser

Mà nên:

DELETE /users/{id}

Safe Method

Safe Method không thay đổi trạng thái hệ thống.

Bao gồm:

  • GET
  • HEAD
  • OPTIONS

Ví dụ:

GET /users

Có thể gọi nhiều lần mà không tạo dữ liệu mới.

Idempotent Method

Một request có thể thực hiện nhiều lần nhưng kết quả cuối cùng không đổi.

Ví dụ:

DELETE /users/10

Gọi 1 lần hoặc 100 lần đều dẫn đến trạng thái “user không còn tồn tại”.

Idempotent:

  • GET
  • PUT
  • DELETE
  • HEAD
  • OPTIONS

Không idempotent:

  • POST

Lưu ý: POST có thể đạt tính idempotent thông qua Idempotency-Key, sẽ được trình bày ở chương riêng.

Richardson Maturity Model

REST có thể được đánh giá theo 4 cấp độ.

Level 0

Một endpoint cho mọi thao tác.

POST /api

Body:

Không khuyến nghị.

Level 1

Có Resource.

/users
/orders

Nhưng vẫn dùng POST cho mọi hành động.

Level 2

Sử dụng đúng HTTP Method.

GET /users
POST /users
PATCH /users/1
DELETE /users/1

Đây là mức mà hầu hết Enterprise API hướng tới.

Level 3

Thêm HATEOAS.

Ít được áp dụng trong thực tế.

Best Practices

  • Thiết kế API theo Resource.
  • Để HTTP Method biểu diễn hành động.
  • Mỗi request độc lập (Stateless).
  • Tận dụng Cache-Control khi phù hợp.
  • Không đưa động từ vào URI.
  • Ưu tiên Richardson Level 2 cho đa số hệ thống.
  • Chỉ sử dụng HATEOAS khi có nhu cầu rõ ràng.

Checklist

  • URI đại diện cho Resource.
  • HTTP Method biểu diễn hành động.
  • API không lưu trạng thái giữa các request.
  • Response có chiến lược cache phù hợp.
  • Không sử dụng động từ trong URI.
  • Thiết kế đạt tối thiểu Richardson Level 2.
  • Client không phụ thuộc vào implementation của Server.
