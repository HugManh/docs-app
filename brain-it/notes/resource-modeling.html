Chương 4. Resource Modeling

Purpose

Resource Modeling là bước quan trọng nhất trong thiết kế REST API. Chất lượng của mô hình Resource quyết định trực tiếp đến tính dễ hiểu, khả năng mở rộng và mức độ nhất quán của toàn bộ API.

Một API thường khó bảo trì không phải vì HTTP hay framework, mà vì mô hình Resource ban đầu chưa hợp lý.

Mục tiêu của chương này là xác định:

  • Thế nào là một Resource.
  • Khi nào nên tạo Resource mới.
  • Khi nào nên gộp hoặc tách Resource.
  • Cách biểu diễn quan hệ giữa các Resource.
  • Cách tránh thiết kế API bám theo Database.

Rules

  • Resource MUST đại diện cho một Domain Concept.
  • Resource MUST có danh tính (Identity).
  • Resource SHOULD có vòng đời (Lifecycle).
  • Resource SHOULD độc lập với Database Schema.
  • Resource SHOULD phản ánh Business Domain.
  • Relationship MUST được mô hình hóa rõ ràng.
  • Aggregate Boundary SHOULD được tôn trọng.
  • Resource MUST NOT được tạo chỉ vì có thêm một bảng trong Database.

What is a Resource?

Resource là bất kỳ đối tượng nào mà hệ thống quản lý và có thể được định danh bằng URI.

Ví dụ:

User
Course
Lesson
Order
Invoice
Comment
Role
Category

Không phải:

SaveUser
Login
Register
DeleteOrder
UpdateCourse

Đây là hành động (Action), không phải Resource.

Một Resource tốt thường có:

  • Identity

  • Lifecycle
  • Representation

Resource vs Table

Không nên thiết kế API dựa trực tiếp vào Database.

Database:

user

user_profile

user_address

user_setting

Không nhất thiết phải có:

/users

/user-profiles

/user-addresses

/user-settings

Có thể chỉ cần:

GET /users/{id}

Response:

Why?

Database tối ưu cho lưu trữ.

REST tối ưu cho giao tiếp.

Hai mục tiêu này không giống nhau.

Aggregate Root

Trong Domain-Driven Design (DDD), Aggregate Root thường là Resource phù hợp.

Ví dụ:

Order

├── Items
├── Payment
└── Shipment

API:

/orders
/orders/{id}

Không nhất thiết:

/payments

nếu Payment không tồn tại độc lập.

Independent Resource

Một Resource nên độc lập nếu:

  • Có Identity riêng.
  • Có vòng đời riêng.
  • Có Permission riêng.
  • Có Business Logic riêng.
  • Có thể truy cập độc lập.

Ví dụ:

Course

Lesson

Lesson có thể:

GET /lessons/20

→ Đây là Resource độc lập.

Embedded Object

Một Object không cần là Resource nếu:

  • Không có Identity.
  • Không có Lifecycle.
  • Chỉ tồn tại cùng Resource cha.

Ví dụ:

Không cần:

/shipping-addresses

One-to-One

Ví dụ:

User

↓

Profile

Có hai lựa chọn.

Option 1

GET /users/{id}

Khuyến nghị nếu Profile không có Lifecycle riêng.

Option 2

GET /profiles/{id}

Khuyến nghị nếu Profile có:

  • Permission riêng
  • CRUD riêng
  • Ownership riêng

One-to-Many

Ví dụ:

Course

↓

Lesson

Có thể:

GET /courses/10/lessons

và

GET /lessons/5

cùng tồn tại.

Many-to-Many

Ví dụ:

Student

⇄

Course

Không nên:

/studentCourses

Thay vào đó:

GET /students/{id}/courses

GET /courses/{id}/students

Nếu Enrollment có dữ liệu riêng:

score
joinedAt
status

thì nên tạo Resource:

/enrollments

Resource Ownership

Ví dụ:

User

↓

Order

Order thuộc User.

Có thể:

GET /users/{id}/orders

Nếu Order cần truy cập độc lập:

GET /orders/{id}

nên tồn tại song song.

Composition vs Aggregation

Composition:

Course

↓

Lesson

Lesson không thể tồn tại nếu Course bị xóa.

Aggregation:

User

↓

Role

Role vẫn tồn tại nếu User bị xóa.

Composition thường phù hợp với Nested Resource.

Aggregation thường phù hợp với Resource độc lập.

Shared Resource

Ví dụ:

Category

được dùng bởi:

  • Course
  • Book
  • Article

Category nên là Resource độc lập.

/categories

Không nên:

/courseCategories

/bookCategories

/articleCategories

Derived Resource

Có những Resource được tính toán.

Ví dụ:

Dashboard

Statistics

Report

Đây vẫn có thể là Resource.

GET /reports/sales

GET /statistics

GET /dashboard

Không nhất thiết phải lưu trong Database.

Virtual Resource

Ví dụ:

/me

Đây là Virtual Resource.

Thực tế:

/users/{currentUser}

nhưng Client không cần biết ID.

Singleton Resource

Có những Resource chỉ tồn tại duy nhất.

Ví dụ:

/system-config

/application-setting

/profile

Không cần:

/system-configs/1

Resource State

Không nên tạo nhiều endpoint cho từng trạng thái.

Sai:

/publishedCourses

/draftCourses

/deletedCourses

Nên:

GET /courses?status=published

GET /courses?status=draft

Resource Granularity

Quá nhỏ:

/user-name

/user-email

/user-phone

Quá lớn:

/everything

Nên cân bằng theo Business Domain.

Anti-patterns

CRUD theo Database

Sai:

users

user_profiles

user_addresses

↓

/users

/userProfiles

/userAddresses

API theo UI

Sai:

/homePage

/dashboardCard

/menuData

UI có thể thay đổi liên tục.

Domain thường ổn định hơn.

God Resource

Sai:

/system

trả về:

  • User
  • Order
  • Course
  • Report
  • Dashboard

Đây là Resource quá lớn.

Best Practices

  • Thiết kế theo Business Domain, không theo Database.
  • Aggregate Root thường là Resource chính.
  • Chỉ tạo Resource khi có Identity và Lifecycle.
  • Embedded Object không nên có endpoint riêng.
  • Quan hệ nhiều-nhiều có dữ liệu riêng nên tạo Resource trung gian.
  • Cho phép Resource được truy cập trực tiếp nếu có ý nghĩa nghiệp vụ.
  • Tránh API phản ánh cấu trúc giao diện người dùng.

Checklist

  • Resource đại diện cho Domain Concept.
  • Resource có Identity.
  • Resource có Lifecycle rõ ràng.
  • Không thiết kế API theo Database Schema.
  • Không thiết kế API theo UI.
  • Embedded Object không có endpoint riêng.
  • Aggregate Root được xác định rõ.
  • Quan hệ nhiều-nhiều có dữ liệu riêng được tách thành Resource.
  • Nested Resource chỉ dùng khi biểu diễn quan hệ sở hữu.
  • Mỗi Resource có phạm vi trách nhiệm rõ ràng.
